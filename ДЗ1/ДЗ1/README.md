Описание архитектуры
Маркетплейс построен как модульный монолит с точечным выделением сервисов. Ядро (Backend) содержит бизнес-логику: пользователей и роли, каталог, остатки, заказы. Такой подход снижает стоимость разработки, развёртывания и поддержки на старте, а чёткие границы модулей позволяют позже вынести любой из них в отдельный сервис. Отдельными контейнерами сделаны те части, где важны скорость и масштабируемость: поиск, персонализация ленты, платежи, интеграции с логистикой и сервис уведомлений. Они масштабируются независимо от ядра, и их сбой не останавливает оформление заказов.
Ключевые решения
Каналы взаимодействия. Клиенты (веб, мобильное приложение, кабинет селлера, админка) обращаются к системе синхронно через три API-шлюза: публичный, seller и admin. Шлюзы напрямую вызывают Backend и сервисы, потому что пользователю нужен немедленный ответ. Взаимодействие между серверными частями идёт асинхронно через брокер сообщений.
Kafka лучше подходит для сложных и высоконагруженных взаимодействий маркетплейса чем условный RabbitMQ: она выдерживает большой поток событий (заказы, оплаты, статусы доставки), хранит их и позволяет нескольким потребителям читать один поток независимо.
PostgreSQL бесплатна, зрелая и хорошо подходит для сильно связанных данных (пользователи, товары, остатки, заказы) с транзакциями и ограничениями целостности.
Elasticsearch обеспечивает гибкий полнотекстовый поиск и фильтрацию по каталогу. Его возможности персонализации ограничены (переранжирование по профилю), поэтому профиль пользователя формирует отдельный модуль, а Elasticsearch применяет его при ранжировании.
Т-касса выбрана как зрелое и распространённое решение для приёма платежей: это снижает риски интеграции и избавляет платформу от хранения карточных данных. Платёжный сервис отвечает за создание платежей, возвраты, журнал операций и приём вебхуков.
Внешние интеграции (логистика, Mindbox) вынесены в адаптеры, которые общаются с Backend только через Kafka, поэтому изменения во внешних API не затрагивают ядро.
Mindbox выбран как удобный в использовании, омниканальный сервис автоматизации маркетинга, рассылок, программ лояльности и персонализации.

Домены, сервисы и их ответственность:
Пользователи и роли - регистрация, аутентификация, профили, доступы - Backend

Каталог - товары, категории и характеристики товаров - Backend

Остатки по товарам - наличие товара и создание резерва при заказе - Backend

Заказы - создание и изменение статуса и номенклатуры заказа - Backend

Поиск -  поиск товаров, персонализация, фильтрация - ElasticSearch

Оплаты - создание платежей, статус и работа с api внешней платформы оплат - Т-касса

Логистика - служба доставки, передача статусов товаров - внешние службы доставки

Уведомления - передача сообщений пользователям/селлерам по поводу конкретных заказов, оплат, маркетинговых сообщений - Mindbox

Маркетинг - акции, программа лояльности, персонализация - Mindbox и отдельный модуль персонализации

Владение данными
Данные(Backend): заказы, товары , категории, профили пользователей, история заказов, история оплат
Данные(Поиск): товары, персонализованная информация, профиль, категории
Данные(Т-касса - оплаты): данные о платежах
Данные(Логистика): данные о заказах
Данные(Mindbox - уведомления): данные по сообщениям, статусы заказов
Данные(Mindbox - маркетинг): профильные данные, история заказов, геоданные

Взаимодействие сервисов:
Backend - Поиск(синхронное), Оплаты(синхронное), Логистика(асинхронное), Уведомления(асинхронное), Маркетинг(асинхронное)
Оплаты - Backend(асинхронное)
Логистика - Уведомления(асинхронное через Back)
Уведомления - Backend(асинхронное)
Маркетинг - Backend(для аналитики - асинхронное)

Синхронное - для быстроты ответа
Асинхронное для экономии ресурсов, отсутствие необходимости максимально скоростного ответа

Альтернативная архитектура:
Полностью основанная на микросервисах - каждый домен - отдельный микросервис. Основное преимущество - скорость разработки, легкая масштабируемость и независимость частей проекта, но главный минус это сложность взаимодействия большого количества сервисов и повышенная цена.

Финальный выбор:
В нашем варианте учитывается использование микросервисов для скорости и масштабируемости с максимизацией удобства и дешевизны монолита.
